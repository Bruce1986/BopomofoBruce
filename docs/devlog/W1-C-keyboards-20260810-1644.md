## 已修正

### C9（high）密碼／URL 鍵盤打不出任何數字

`password_qwerty.json` / `url_qwerty.json` 原本 27／28 個 Character 鍵裡 0 個數字。改法：兩份
JSON 的 q-p 十顆鍵各加 `longPress`，值為 Gboard 慣例的 1-0（q→1, w→2, …, p→0），不改任何短按
action、不動 `:common`。

新增測試 `OtherKeyboardsContentTest.password and url keyboards can type every digit 0-9 and stay
pure ASCII`：對 `passwordQwerty` / `urlQwerty` 各收集「可達字元」（短按 action + longPress action
皆為 `KeyAction.Character` 時取其 char），斷言涵蓋 `'0'..'9'` 全部十個，且所有可達字元皆為 ASCII
（`code <= 127`）。

**已證明會紅**：暫時把 `password_qwerty.json` 的 `p` 鍵（對應數字 `0`）longPress 拿掉，重跑後
2 個測試失敗——新增的 C9 測試本身，以及既有的 `password and url keyboards share identical qwerty
letter rows`（因為改動只動了 password 這邊，兩份鍵盤的字母列因此不再逐鍵相等，屬預期的連帶失敗，
不是新測試設計錯誤）。還原後 `git diff` 乾淨、全綠。

### C8（high）loader 的 strict 契約零覆蓋

`KeyboardLoaderTest` 兩條 strict 測試原本用測試檔自己的 `private val json`（未經過
`KeyboardLoader`），所以 `KeyboardLoader` 的 `ignoreUnknownKeys=false` 契約沒有任何測試真的釘住。

改法：在 `KeyboardLoader` 新增 `internal fun decode(text: String): KeyboardDef`，
`loadFromResource` 改呼叫它；兩條 strict 測試改成呼叫 `KeyboardLoader.decode(malformed)`，讓斷言
真的穿過 loader 本身的 `json` 實例。

**實測證明（本輪最重要的一步）**：把 `KeyboardLoader.json` 暫時改成
`Json { prettyPrint = false; ignoreUnknownKeys = true }`，重跑 `:keyboards:testDebugUnitTest`：

```
KeyboardLoaderTest > strict schema validation actually rejects an unknown field() FAILED
    org.opentest4j.AssertionFailedError: Expected kotlinx.serialization.SerializationException to
    be thrown, but nothing was thrown.

BUILD FAILED in 635ms
```

同一次跑，其餘 27 個 test case（含 `strict schema validation rejects an unknown KeyAction
discriminator`）皆 PASSED——只有「unknown field」這條變紅，「unknown discriminator」那條沒有變紅。
還原 `ignoreUnknownKeys` 後全 28 條測試綠、`git diff` 對 `KeyboardLoader.kt` 只剩 `decode` seam
那 12 行新增。

這個實測結果同時是 C10 要更正的依據，見下方。

### C10（medium）devlog 把未查證推測寫成事實

`docs/devlog/W1-C-keyboards-20260810-0714.md` 的「schema 驗證這一項如何證明」段落原本宣稱「兩者
若把 `ignoreUnknownKeys = true` 打開就會轉綠變紅」——對 loader 不成立，因為那兩條測試當時用的是
測試檔自己的 `json`，跟 `KeyboardLoader` 完全無關，開不開 `ignoreUnknownKeys` 對它們的行為都
沒有影響（它們本來就用自己的 strict `Json`，不管 `KeyboardLoader` 怎麼設定）。

修正後、依 C8 的實測結果：現在（改完 C8 之後）把 `ignoreUnknownKeys` 打開，**只有** `unknown
field` 那條測試變紅；`unknown discriminator` 那條測試維持綠，因為它的失敗來源是 polymorphic
`KeyAction` serializer 找不到 `"not_a_real_action"` 這個 discriminator 對應的子型別，這件事跟
`ignoreUnknownKeys` 完全無關（哪怕 `ignoreUnknownKeys=true`，未知的 sealed class 判別值一樣會讓
`decodeFromString` 拋 `SerializationException`）。已在 `KeyboardLoaderTest.kt` 該測試上方補一行
comment 講清楚這件事，避免下一個人重蹈覆轍。

## 未動、留給 lead / `:ime`（W2-B）裁決

### C11（medium）qwerty 各列 weight 總和不一致

password 四列 weight 總和為 10 / 9 / 9.6 / 7.6，url 為 10 / 9 / 9.6 / 8.8。依 `KeyData` KDoc
「row 內水平寬度比例（同 row 加總後分母化）」的語意，三列字母鍵單獨看會各自分母化成 1/10、1/9、
1/9.6，鍵柱左右理論上會錯開。

**選擇方案 (b)**：不動 JSON 資料、不新增假鍵，把「跨列的鍵柱對齊由 renderer（`:ime`）負責」這個
約定明確寫進 `Keyboards.kt` 的 `passwordQwerty` / `urlQwerty` KDoc（已完成，見上方 diff）。

**理由**：

1. `KeyData`／`KeyboardDef` 目前的模型只定義「同一 row 內的相對寬度比例」，沒有 spacer/gap 這種
   「跨 row 對齊留白」的概念——這是 `:common` 的模型範圍，`:keyboards` 子代理依規則不能動
   `:common`，也不該為了對齊硬塞一個假的 `KeyAction.Custom("spacer")`。
2. 若用假 spacer 鍵，`:ime` 沒有義務認得這個 id，一旦誤把它當成正常鍵 render 出來，使用者會看到
   一顆按下去沒反應（或送出未知 custom action）的空鍵，比「鍵柱沒精準對齊」這個純視覺瑕疵更糟、
   更容易被誤認成 bug。
3. 末列（7.6 vs 8.8）本身鍵組就不同（password 是 123/space/./enter 四鍵，url 多了 `/` 跟
   `.com` 變六鍵），這兩列的 weight 總和不對齊是設計上就該有的差異，不在本次要處理的範圍內
   （驗證者已確認這點，不該要求對齊）。
4. 字母三列（10/9/9.6）沒有鍵數差異的正當理由（都是純字母 + 極少數控制鍵），是三顆 QWERTY 標準
   鍵盤本來就會有的階梯形收尾——這是 renderer 該處理的視覺對齊問題（例如依最大列寬正規化、或用
   容器 padding 讓短列置中/靠左對齊），不是資料模型該解的問題。

**登記為 W2-B（`:ime`）follow-up**：`:ime` 實作 renderer 時，字母三列（q-p / a-l / z-m）的鍵柱
視覺對齊需要 renderer 自行處理（例如以最寬列的總 weight 為分母正規化其餘列，而不是各列各自
分母化），`Keyboards.kt` 的 KDoc 已加註此約定供 `:ime` 開發時參照。
