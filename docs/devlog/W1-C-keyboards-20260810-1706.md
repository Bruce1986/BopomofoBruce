## 已修正

### D1（high）url_qwerty 打不出 URL 必要的半形符號

`url_qwerty.json` 原本可達的非英數字元只有 `/` 與 `.`（C9 只加了數字）。缺 `: - _ ? = & # % ~ @`
這組——`http://`、`my-site.com`、query string 全部打不出來，而唯一的出口「123」指向的
`symbol_standard` 全形頁裡剛好有外觀相似的全形孿生體（`：` `－` `＆` `＝`…），使用者很容易誤以為
按對了鍵。

### D2（medium）password_qwerty 同理，打不出密碼常見特殊符號

`password_qwerty.json` 可達的非英數只有 `.`，`! @ # $ % ^ & * ( )` 全打不出來，而密碼欄位遮罩顯示
讓誤打全形字元幾乎不可能自行發現。

**D1/D2 合併改法**：兩份 JSON 的 `q-p` 十顆鍵已在 C9 掛了數字 longPress，本輪改在 `a-l`（9 鍵）與
`z-m` 的字母鍵（`z x c v b n m`，7 鍵，`⇧`/`⌫` 不動）上補 longPress，總共 16 個插槽。既有測試
`password and url keyboards share identical qwerty letter rows` 用 `rows.take(3)` 逐鍵比對
password/url 的字母列必須相等，所以這兩份 JSON 在 `a-l`/`z-m` 上的 longPress **必須完全一致**——
因此本輪選了 D1（url 10 個）∪ D2（password 10 個）的聯集（扣掉重複的 `@ # %` 後恰好 16 個），一次
塞滿 16 個插槽，兩份鍵盤各自超集涵蓋自己那條 finding 要求的最小集合：

| 鍵 | longPress | 鍵 | longPress |
| --- | --- | --- | --- |
| a | `:` | z | `&` |
| s | `-` | x | `!` |
| d | `_` | c | `$` |
| f | `?` | v | `^` |
| g | `=` | b | `*` |
| h | `~` | n | `(` |
| j | `@` | m | `)` |
| k | `#` |  |  |
| l | `%` |  |  |

**理由**：
1. 不新增鍵位、不動 `:common`，只用既有的 `KeyData.longPress` 契約（比照 C9）。
2. 放在字母列（`a-l`/`z-m`）而非各自的控制列，是因為控制列本來就不同（password 4 鍵 vs url
   6 鍵），若把差異化符號硬塞進控制列，將來還是要各自維護一份，等於繞開既有「字母列必須相等」
   這條測試想守住的不變量；直接讓兩邊共享同一份聯集，兩邊都超集滿足、也不必再新增例外。
3. 聯集恰好 16 個、插槽恰好 16 個，沒有多餘或不足，不需要決定「哪個符號犧牲不放」。

新增測試：
- `url keyboard can type the half-width symbols needed for a query string`（斷言
  `: - _ ? = & # % ~ @` 皆可達，短按或長按）
- `password keyboard can type common half-width special symbols`（斷言
  `! @ # $ % ^ & * ( )` 皆可達，短按或長按）

**已證明會紅**：
- 暫時拿掉 `url_qwerty.json` 的 `j` 鍵（`@`）longPress，重跑後
  `url keyboard can type the half-width symbols needed for a query string` 與既有的
  `password and url keyboards share identical qwerty letter rows` 兩條變紅（後者是預期的連帶失敗，
  改動只動了 url 一側，字母列不再逐鍵相等，與 C9 round 3 的教訓一致）；還原後兩條皆綠。
- 同樣手法對 `password_qwerty.json` 的 `x` 鍵（`!`）做了一次，`password keyboard can type common
  half-width special symbols` 與字母列相等測試皆如預期變紅；還原後皆綠。

### D3（medium）注音鍵盤「英數」鍵沒有落點——登記為交接缺口，不新增鍵盤

把 `Keyboards.all` 過一遍確認：`zhuyin_4x10_portrait`/`zhuyin_4x10_landscape`/`symbol_standard`
三份 JSON 裡都有 `language_toggle`（`grep -n "language_toggle" keyboards/src/main/resources/keyboards/*.json`
證實，行號各自為 zhuyin_4x10_landscape.json:382、symbol_standard.json:224、
zhuyin_4x10_portrait.json:310），但 `Keyboards.all`（`Keyboards.kt`）裡沒有任何通用英文字母鍵盤——
`passwordQwerty`/`urlQwerty` 是 InputType 綁定的專用鍵盤（結構上等同英文 QWERTY，但
`:ime` 不該把它們當一般文字欄位的英文鍵盤用）。對照 `docs/DEVPLAN-SubagentFanout-20260620-0851.md`
第 246-263 行的 W1-C 驗收清單（「注音 4×10、標準符號、數字鍵盤、密碼鍵盤、電話、URL、日期時間」），
確認**通用英文鍵盤本來就不在 W1-C 交付範圍內**，這是交接／文件缺口，不是本輪要新增一份鍵盤。

**登記為 lead / W2-B（`:ime`）follow-up**：`language_toggle` 的目的地鍵盤不在 W1-C 交付範圍，
`Keyboards.all` 目前沒有對應項；`:ime` 接線 `language_toggle` 前需先確認由哪個工作包補上通用英文
鍵盤，否則注音鍵盤的「英數」鍵會無落點（按下去沒有對應的 `KeyboardDef` 可以切換過去）。

### D4（medium）重複鍵偵測改用 reachableChars，涵蓋 longPress

既有的 `no keyboard has a duplicate Character key` 測試原本只掃 `key.action`，忽略 `longPress`。
C9 一次新增 20 個 longPress Character 鍵、本輪 D1/D2 再加 32 個（兩份 JSON 各 16），全部落在該測試
的偵測範圍外，而這條測試的用途正是抓 password/url 複製貼上的錯誤——longPress 正是最容易貼錯的
地方。

改法：把該測試的 `charActions` 來源從「只掃短按 `key.action`」改成呼叫既有的 `reachableChars`
helper（第 62 行，涵蓋短按 + longPress），兩套「這個鍵盤能打出哪些字元」的定義合而為一，不再有
第二把不同的尺。

**已證明會紅**：暫時把 `url_qwerty.json` 的 `k` 鍵 longPress 從 `#` 改成 `@`（與 `j` 鍵重複），
重跑後 `no keyboard has a duplicate Character key` 變紅（同時連帶讓
`url keyboard can type the half-width symbols needed for a query string` 也變紅，因為 `#`
不再可達——預期行為，不是新測試設計錯誤）；還原後 `git diff` 乾淨、全綠。

**實測結果**：改用 `reachableChars` 後重跑 `:keyboards:testDebugUnitTest`，8 份鍵盤（含本輪改動過
的 password/url）皆無重複——tracer 靜態核對的結論與本輪實跑結果一致，是零行為變更（在「今天沒有
真的重複」這件事上），但偵測範圍本身確實擴大了（見上方紅綠證明）。
